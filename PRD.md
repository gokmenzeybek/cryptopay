**Purpose:** This document is the single source of truth for making CryptoPay production-ready. It is written to be executed by an AI coding agent (possibly a small model, possibly across many sessions) with no prior context. Everything the executing agent needs is in this file plus the repository.

## 0. RULES FOR THE EXECUTING AGENT — READ FIRST, BEFORE ANY WORK

### 0.1 Checkbox protocol (mandatory)

- This document uses `- [ ]` checkboxes for every subtask. **When you finish a subtask, you MUST immediately change `- [ ]` to `- [x]` for that subtask** and append a completion note on the same line in this format: `— done <date>; verification: <command run + result>`.
- **Never tick a box you did not fully complete and verify.** A box may only be ticked if the subtask's "Verify:" step was actually executed and passed. If you cannot run the verification, the subtask is NOT done — see 0.4.
- Never tick a box "in advance" because you are about to do the work, and never batch-tick several boxes at the end of a session. Tick each box the moment its verification passes.
- Updating this file (ticking boxes, status section, blocked notes) is the ONLY documentation you are required to maintain. Do not create additional markdown reports unless the user asks.

### 0.2 Definition of Done (applies to every subtask)

A subtask is DONE only when ALL of the following hold:

1. The described change is fully implemented — no stubs, no TODOs, no placeholders.
2. Its **Verify:** step (listed in the subtask) was run and passed, and the result is recorded on the checkbox line.
3. You did not break anything that previously worked: run the most relevant existing tests (unit tests for the touched module, or `npm test` if the change is cross-cutting). If the baseline test suite was already failing for unrelated reasons (see §2), your change must not add NEW failures.
4. The change follows the repo conventions (§0.5).

### 0.3 When to proceed

- Work **one subtask at a time**, in the order listed within a phase.
- Proceed to the next subtask only after the current one is ticked (done) or marked BLOCKED (see 0.4).
- Phases must be executed in order (1 → 7). Do not start Phase N+1 while Phase N has unticked, unblocked subtasks — unless the user explicitly tells you to skip or reorder.
- Some subtasks are marked **(PARALLEL-OK)**; those may be done in any order relative to their siblings.

### 0.4 Failed / blocked subtasks

A subtask is FAILED/BLOCKED when any of these is true:

- Its verification fails **3 times in a row** despite genuine fix attempts.
- It requires an external resource you do not have (real Papara production credentials, third-party account, user decision).
- Implementing it would require violating a guardrail in §0.5.

When blocked, you MUST:

1. **Leave the box unticked.** Edit the subtask line to read: `- [ ] **BLOCKED <date>:** <one-line reason> — <original subtask text>`.
2. Add an entry to the **Blocked items** list in §1 (Current Status).
3. If the subtask is marked **(CRITICAL PATH)**, STOP all work and report to the user. Do not skip ahead.
4. If not critical-path, continue with the next subtask and mention the blockage in your next user-facing message.

**Never** "fix" a failing verification by weakening it: do not delete assertions, lower coverage thresholds, loosen regexes in the verification commands, mock the thing being tested in production code, or comment out failing tests. That is the single most common way a small model corrupts this process.

### 0.5 Hard guardrails (never violate, no exceptions)

1. **No git mutations.** Never run `git commit`, `git push`, `git reset`, `git rebase`, `git checkout --`, or `git clean`. Reading git state (`git status`, `git diff`, `git log`) is fine.
2. **Never modify `.env`** (the live secrets file). Configuration changes go into `.env.example`, `docker-compose*.yml`, or docs. Never print or copy secret values anywhere.
3. **Off-limits files** (unless a subtask explicitly names them): `jest.config.js` coverage thresholds, anything under `tests/` and `**/__tests__/` (test edits only happen in Phase 7 subtasks or when a subtask explicitly says to add a test), `database/schema.sql` history (append-only changes via migrations where possible).
4. **Minimal diffs.** Fix what the subtask describes, nothing more. No drive-by refactors, renames, reformatting, or "improvements" to adjacent code.
5. **Repo conventions** (match them, do not invent new style): backend is CommonJS with JSDoc-style block comments; API responses use the `{ success: boolean, ... }` envelope; errors go through `catchAsync`; logging through `utils/logger.js` (Winston) — never add `console.log` to server code; layering is routes → `services/` → `database/dal/` (no SQL in routes, no business logic in DALs); all SQL uses parameterized queries.
6. **No new dependencies** without user approval. Check `package.json` first; the needed library is almost always already there.
7. **The app targets XRPL testnet.** Do not switch anything to mainnet endpoints. (Mainnet readiness is explicitly out of scope — see §8 Open Questions.)
8. If this document and the code disagree, trust the code and note the disagreement in §8 rather than silently "fixing" the doc.
9. If you are unsure whether an action is allowed, it is not. Note it in §8 and continue with the next subtask or ask the user.

### 0.6 Session handoff protocol (mandatory at end of every work session)

Before you stop working (user says stop, context runs low, or you are blocked), you MUST update §1 (Current Status):

- `Last completed subtask:` the ID of the most recently ticked box.
- `Next subtask:` the ID of the first unticked, unblocked subtask.
- `Working state:` anything a fresh agent could not rediscover in 2 minutes — e.g. "server won't boot until X is set", "left a TODO comment at file:line", "tests currently red because of Y".
- `Blocked items:` current list from 0.4.

A new session should be able to read §1 and resume in under 5 minutes without re-auditing the repo.
